# Материалы следующей контрольной точки

По заданию после завершения проекта потребуются презентация на 10–15 слайдов и отчёт на 20–25 страниц: что сделано и что команда планирует на следующие четыре недели. Ниже готова содержательная основа, привязанная к фактической Final 1.0.

## Презентация: 12 слайдов

### 1. SkyShelf · Final 1.0

Защищённое облако для учебных команд. Команда, группа ЭФБО-14-24, роли участников. Визуал: стеклянное облако и одна ключевая фраза — «От первой идеи до готовой сдачи».

### 2. Проблема

Материалы проекта находятся в чатах, заметках и разных облаках. Теряются версии, ответственность и итоговый файл. Покажите три крупные карточки: «версии», «команда», «сдача».

### 3. Цель и аудитория

Цель — единое пространство проекта с защищёнными файлами и контролируемой сдачей. Аудитория: студенты, учебные команды, кураторы и преподаватели.

### 4. Путь пользователя

Создать проект → пригласить команду → собрать файлы и версии → выполнить чек‑лист → выбрать финал → передать преподавателю.

### 5. Что реализовано

Файлы/папки/поиск, версии, избранное, корзина, квоты, роли, чек‑лист, кастомизация, итоговый файл, ZIP, ссылки, аудит, 2FA и админ-панель. Не превращайте в сплошной список: используйте 6–8 плашек.

### 6. Студенческие отличия

Сравните с обычным диском: предмет и преподаватель, дедлайн, прогресс сдачи, единый final, преподавательская карточка, роли учебной команды. Основной тезис: SkyShelf организует процесс, а не только хранит байты.

### 7. Защита данных

Схема: Argon2id → аккаунт; AES‑256‑GCM → файлы и TOTP-secret; SHA‑256 → целостность; TOTP → второй фактор; hashed token + expiry/password/limit → публичная ссылка; RBAC + CSRF → запросы.

### 8. Архитектура

Frontend HTML/CSS/JS → Java 17/Spring Boot REST → PostgreSQL/H2 + MinIO/local objects. Подчеркните модульный монолит и закрытый object storage.

### 9. Ключевые экраны

Коллаж: landing, личные файлы, рабочее пространство проекта, безопасность и teacher card. После Figma-доработки заменить на финальные скриншоты.

### 10. Проверка результата

Покажите сквозной сценарий: загрузка → зашифрованный объект → версия → роль читателя → защищённая ссылка → финал → backup/restore. Отдельно указать, что автоматический HTTP smoke работает с изолированной временной БД.

### 11. Итоги команды

- Лев: приоритеты, границы, координация и защита;
- Сергей: требования, бизнес-сценарии, конкуренты, критерии приёмки и отчёт;
- Александр: frontend, backend, безопасность, тестирование и сборка.

Добавьте фактические даты/затраты из доски команды перед сдачей.

### 12. Следующие четыре недели

Неделя 1 — UX/Figma и пользовательская проверка; неделя 2 — миграции/SQL и Docker; неделя 3 — HTTPS, секреты и backup/restore; неделя 4 — visual QA, исправления, отчёт и репетиция защиты.

## Артефакты для приложений отчёта

- диаграмма архитектуры и ER-модель из `ARCHITECTURE.md`;
- матрица ролей;
- список REST-маршрутов из `API.md`;
- таблица мер защиты из `SECURITY.md`;
- протокол smoke-теста из `TESTING.md`;
- скриншоты desktop/mobile после локального browser smoke;
- фрагменты интерфейса из Figma;
- backlog следующих четырёх недель;
- ссылка/QR на репозиторий и стенд, если они будут созданы командой.

## Что писать как выполненное

- рабочий локальный продукт Final 1.0;
- реальные серверные операции, а не localStorage;
- точное скачивание байтов;
- серверные роли и изоляция;
- версии, student workspace, финал и teacher link;
- прикладное шифрование объектов и проверка целостности;
- 2FA, хешированные токены, аудит;
- стартовые скрипты, готовый JAR и документация;
- автоматический HTTP smoke и локальный backup/restore.

## Что не выдавать за выполненное

- публичный HTTPS deployment;
- production key management и автоматическая ротация;
- антивирус;
- end-to-end encryption;
- проверенный PostgreSQL/MinIO restore;
- независимый pentest;
- реальные платежи и почтовые приглашения;
- пользовательское исследование, пока команда его фактически не проведёт;
- визуальный browser smoke на Windows, пока он не будет запущен и зафиксирован.

Такое разделение усиливает защиту: команда показывает инженерную честность и понимает разницу между учебной финальной версией и публичным production-сервисом.
